# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [2.0.0] - Unreleased

Version 2.0.0 gathers everything developed since 1.4.0, including the work that was planned as 1.5.0 (the
section further down, dated 2026-09-04, which was never published under that number). It is a major version
because some things that worked before now behave differently for whoever already used ForZip, mostly in
scripts that call the command line:

### Breaking changes

- **The CLI rejects unknown options and algorithms** instead of ignoring them: a script that passed a misspelt option now stops with the list of valid ones.
- **The CLI rejects an option given twice**, also under its two names (`-p a --password b`): before, the last one silently won, so `zip -i a -i b` packaged only `b`. The only exception is `zip -i`, which now takes several sources (below).
- **A package is never written over an existing one**: if the output, any of its volumes, its manifest or its report already exists, `forzip zip` stops with the list of what is there (the GUI suggests a free name). Scripts that repackaged over the same name must delete the old package first or choose another name.
- **New exit codes**: `forzip zip` returns 3 when the package is incomplete (files the antivirus blocked, folders Windows did not let it read); `forzip verify` returns 2 for an incomplete verification and 3 for an altered package or envelope.
- **Links and junctions inside a selected folder are not followed**: they are recorded among what was not included, with their target.
- **.NET 10** instead of .NET 8 (the published executables are self-contained, so nothing has to be installed).
- The Reserved profile and simple mode always package as ZIP; `--profile reserved` with `--format 7z` is rejected.
- **A package is the archive plus its manifest — two files instead of four.** The `.report.txt` and its `.report.txt.sha256` are no longer written next to every package (nor put inside the `.fzs` envelope): verification only ever used the manifest, so an edited report went unnoticed, and its `.sha256` could be recomputed by whoever edited it. The text report is now generated on request — *Save report…* on the result screen and on Verify, or `forzip verify -m … --write-report <file>` — and the one made from Verify records that verification's verdict. What proves a package did not change is an anchor outside ForZip: the package SHA-256, which the result screen and the delivery act now point out as the value for the chain of custody record, or the manifest signature.
- **`forzip zip` writes the manifest with `--hash`** (it used to need `--report`); `--report` is optional and writes the text report without a `.sha256`. `--no-sidecar` no longer exists for `zip` and is rejected (it stays for `forzip hash`). `--profile reserved` with `--report` is rejected: the report would sit in the clear next to the envelope.
- **Extract and Verify from the context menu open their own window**, like *Calculate hash* (and like 7-Zip and WinRAR), instead of the whole of ForZip. *Extract here* and *Extract to subfolder* start by themselves and end with the result and its observations; an encrypted archive asks for its password on its card. *Extract…* waits for the destination to be confirmed. *Verify* starts by itself and shows the verdict, the details, *Save report…* and, when needed, the password field. Several selected files go to one window and are processed one at a time. The work is logged in the same activity log, redacted when the saved profile is Reserved. Packaging and opening an envelope still use the full window.
- **The report can be an HTML page.** *Save report…* (and `--report` / `--write-report` with a `.html` name) writes a self-contained page that a judge or prosecutor opens with a double click and prints on A4, with the package fingerprint and the verdict at the top. It runs no scripts and loads nothing from outside (a Content-Security-Policy forbids it), every value is escaped, and the page says it presents the manifest and is neither signed nor verified. It carries the ForZip icon inside it for the browser tab. The report saved from Verify is suggested as `case.zip.verificacion.html` (`.verification.html` in English), so it does not clash with the packaging one, and an existing name gets a "(2)". The `.txt` is still available.
- **Verify asks for the password before verifying an encrypted package.** When the manifest records that the package has a password and none was typed, nothing is verified and the screen says so ("Password required"), instead of an incomplete verification that guessed the password was "most likely" missing.
- **Manifest schema 1.4**: every manifest now records the packaging environment (computer, Windows version, OS user and local time with its offset), which used to live only in the report. Manifests 1.1 to 1.3 still verify; a report generated from one of them says the environment was not recorded instead of showing the current computer's. Packages from earlier versions, with their four files, verify exactly as before, report `.sha256` included.


### Added

- **The licences travel inside the executables**: ForZip's own (Apache 2.0), its NOTICE, the third-party notices and the UnRAR licence, shown by *About → Licencias* and by `forzip --licenses`. Updating from 1.4 replaces only `ForZip.exe`, and the CLI may circulate on its own, so the files next to them could be missing or out of date.
- **The output name follows the chosen folder.** When the suggested name got a "(2)" because of a clash next to the source and the operator picked another folder without touching the name, the "(2)" travelled along; it is now recalculated for the new folder. The same happens the other way round: a name that clashes in the new folder gets its "(2)" there, instead of Windows asking whether to replace a file ForZip would never replace. A name the operator typed is kept as is.

- **`forzip zip` takes several sources**, like the multiple selection of the GUI: `forzip zip -i acta.pdf -i ./photos -o case.zip`. With more than one source, `-o` is required; the same source twice is refused.
- **7z packages, written and read by ForZip's own engine.** Packaging can now produce a `.7z` instead of a ZIP (GUI: *Package format* in advanced mode; CLI: `--format 7z`, or simply `-o case.7z`), with the same forensic guarantees as the ZIP path: each file is read once and feeds the hashes and the compressor in the same pass, files the antivirus blocks or that vanished since selection are documented as omitted, empty folders are kept, multi-volume output (`.001`, `.002`, …) is supported with a SHA-256 per volume, and a failed or cancelled run leaves nothing on disk. 7z packages use LZMA2 without solid mode — damage to one file never spreads to the next — and every core: in a test set of 1,437 files (78 MB) the 7z took 7.8 s against 14.6 s for the ZIP. With a password, AES-256 also encrypts the **file names**, so without the password not even the contents list is visible. The manifest declares schema 1.3 with `"ArchiveFormat": "7z"`; a ZIP manifest is byte-for-byte what it was. The report names the format, its global hash and the encryption of names.
- **Opening and verifying 7z.** Extract and Verify accept `.7z` (also split into volumes, and also archives made by 7-Zip), recognised by the file signature rather than the extension. Verification of a 7z is per file and resilient: a damaged file is reported as altered and the rest are still verified, since each file is compressed independently. The Explorer context menu offers the archive actions on `.7z` too, under `SystemFileAssociations`, without touching 7-Zip's own association.
- The engine, PrZip (git submodule `PrZip/`, published at https://github.com/PatagoniaRobot/PrZip), has no external dependencies. Its ported code is the public-domain `C/` folder of Igor Pavlov's LZMA SDK; the RAR reader, a declared port of unrar 7.3.1 that lives in a separate assembly under the unrar license (`LICENSE-UNRAR.txt`: it may read RAR in any software, never create it); and the 512-number randomisation table of bzip2 1.0.8, with its BSD-style notice. Everything else is its own code, and what `7zFormat.txt` does not document was established by black-box tests against 7-Zip, never from its source. It was cross-checked against 7-Zip 24.08 on 16 read modes and 13 write modes.
- **Opening evidence in TAR, TAR.GZ/BZ2/XZ, GZ, BZ2, XZ and ISO.** Extract recognises these formats by their signature and extracts them with the same guarantees as a ZIP: nothing is written outside the destination and a failed or cancelled run leaves nothing behind. Compressed formats verify their own checks (CRC32 for GZip, block CRCs for BZip2, CRC32/CRC64/SHA-256 for XZ), including inside a `.tar.gz`, where the reader goes on to the end of the stream even after the TAR has finished. What does not come out as it was is documented in the activity log and on the console instead of aborting: names that are dangerous or invalid on Windows (absolute paths, `..`, reserved names) are sanitised and listed with their original form, two entries with the same name are both kept, and symbolic and hard links, devices and FIFOs are not created but listed. ISO images (ISO 9660 with Joliet names) are checked against hostile structures such as directory loops or extents outside the image. Plain TAR and ISO carry no checksum of their contents: an altered byte inside them cannot be detected by any tool. The context menu offers the archive actions on these extensions too.

- **RAR comments and NTFS streams are reported.** A RAR archive's comment — the archive comment of every version, and the per-file comments RAR 1.5–2.x allowed — is read and written to the activity log (and printed by `forzip unzip`); a comment that is damaged or cannot be read is reported as such and never stops the extraction. NTFS alternate data streams saved with `rar -os` are listed as `file:stream` with their size among the entries that are not created, so a `photo.jpg:Zone.Identifier` (where the file was downloaded from) no longer disappears without a trace. Streams are reported, not extracted. Control characters in a comment are shown as `?`, since whoever made the archive wrote it. Along the way, RAR 1.5–2.x archives with per-file comments no longer fail with "damaged header": UnRAR itself counts an error on them, but their header checksum covers only up to the file name, as RAR 2.90 and its technical note agree.
- **Opening RAR, every version.** Extract now opens RAR archives from RAR 1.5 to WinRAR 7 — stored, every compression method (including RAR 3.x PPMd and its filters, and RAR 2.0 multimedia), solid archives, self-extracting `.exe` archives, encrypted files and encrypted headers (RAR 1.3 to 5.0) and multi-volume sets in both naming schemes (`.part1.rar`, `.r00`), which can be opened from any volume: ForZip starts from the first one and says so if a volume is missing, instead of silently skipping what it cannot reach. Every file is checked against its CRC32 or BLAKE2sp, and with RAR5 a wrong password is told apart from damaged data. Names and links get the same treatment as the other third-party formats. The reader is a declared port of RARLAB's own UnRAR 7.3.1 decompressor, kept in a separate component (`PrZip.Rar.dll`) under the UnRAR license, which allows it in any software that handles RAR archives but not to create them — ForZip only reads RAR. It was cross-checked against UnRAR 7.01 on 173 MB of real data in RAR4 and RAR5, solid, PPMd and multi-volume (identical output), on fixtures made with Rar 2.90, 6.24 and 7.01, and on libarchive's 100-file test corpus, many of them hostile.

- **The active profile is shown everywhere.** A badge at the foot of the sidebar (and the window title) says which confidentiality profile is in force, in every section; Reserved is filled in violet. The profile is chosen in Compress but governs the activity log of the whole application, so it was possible to extract and verify a whole batch under Reserved without knowing it. Leaving Reserved is now recorded in the log, as entering it already was.
- **Verify accepts envelopes and packages directly.** Drag in or choose a `.fzs` envelope or its receipt, a report, a manifest or the package itself — ZIP, 7z or any of its volumes, not only `.001` — and ForZip finds the manifest next to it. Before, the GUI picker and drop zone only took `.txt` and `.json`, so an envelope could only be verified from the Explorer context menu. The section title, labels and picker are translated.
- **Extract accepts self-extracting RAR archives and `.r00`-style parts** by drag and drop and in the picker. An `.exe` is accepted only if a RAR signature is found inside it; it is read, never run. The context menu does not offer them on purpose.
- **Password fields can be shown** (eye button) in Extract, Verify and the operator dialog's certificate password, and **Enter** extracts or verifies.
- **The activity log in its own window.** A new button on the log bar opens it as plain text that follows the log live: any part — a word, a path, several lines — can be selected and copied with Ctrl+C or the right-click menu, and *Copy all* takes everything. In the log at the bottom, several rows can be selected (Ctrl+click, Shift+click) and copied in log order. Errors and warnings are now coloured on the whole line, not only the level word.
- **Hash Batch and the quick hash take folders.** Folders can be dropped or chosen with the new *Folder…* button, and *Calculate hash* from the context menu on a folder now lists its files; each file keeps its relative path, links are not followed and go to the report as omitted, as when packaging. Before, folders were silently dropped.
- **Verify from the context menu on a manifest and on volumes from `.002` on.** A `.manifest.json` offered only Compress and Seal; volumes after the first offered nothing. The new entries need the integration to be re-registered (Settings → Integration: off and on).
- **Self-extracting 7z archives, read without running them.** A `.exe` with a 7z inside — 7-Zip's own SFX module, also with encrypted names (`-mhe=on`) — can be extracted and verified like a `.7z`. ForZip finds the 7z by its signature and checks its start-header CRC, so the six signature bytes appearing by chance inside the program do not fool it; the executable is never run. An `.exe` with neither a 7z nor a RAR inside is still refused. Tested against real 7-Zip 24.08 SFX archives.
- **Verify tests any archive without a manifest**, as `7z t` does: ZIP, 7z, RAR, TAR, GZ, BZ2, XZ, ISO and self-extracting 7z or RAR. Everything is decompressed in memory, nothing is written to disk, and each file's own check (CRC32, AES authentication, BLAKE2sp) is verified. The verdict says how far that goes: *Archive without errors* or *Archive damaged*, never "evidence intact", because without a manifest it cannot be said to be the original; the archive's SHA-256 is shown to be written down. TAR and ISO carry no checksums and are reported as read in full, not as unchanged. An encrypted archive asks for its password; a missing volume is named. A wrong password is stated as such for RAR5, which stores a password check value; for ZIP, 7z and older RAR, where a wrong password and damaged data cannot be told apart, the message says so instead of calling the archive damaged (with 7-Zip's encrypted names, a wrong password used to come out as "damaged"). Before, Verify answered "nothing to verify against" and tested nothing. `forzip verify -i <archive>` does the same (exit code 0 no errors, 3 damaged, 2 not fully tested); with the manifest next to the package, it still verifies against the manifest.
- **Folder fingerprint.** Hash Batch, the context-menu quick hash and `forzip hash -i <folder>` show, for every folder hashed whole, the **ForZip fingerprint** — the SHA-256 of the sorted `sha256sum`-style list of its files and relative paths, which changes if a byte, a name or a location changes — and 7-Zip's **SHA256 for data**, to check against `7z h -scrcSHA256`. The 7-Zip value was established with black-box tests against 7-Zip 24.08 (the sum of the files' SHA-256 as little-endian 256-bit numbers, with the overflow count), never from its source. Both go into the report and are specified in `Documentation/Huella_de_Carpeta_v1.md`, with a dependency-free reference script, `Tools/huella_carpeta.py`, that the tests cross-check. A folder with a file that could not be read gets no fingerprint rather than one that does not cover it.
- **Extract shows the file being extracted** under the progress bar, above the byte count, in the context-menu window and in the full window (ZIP, 7z and the other formats). A long path is cut at the start so the name stays readable; the full path is in the tooltip.
- **Verify has *Clear* and *Open folder*.** *Clear* puts the screen back as it opens, so the previous verdict cannot be taken for the next file's; after *Save report…*, *Open folder* shows the report selected in Explorer (also in the context-menu window).
- **Running as administrator is flagged.** Windows does not let Explorer drop files into an elevated window, and each context-menu action then opens another window instead of reaching this one. ForZip does not need administrator rights; when it runs elevated, the status bar and the log say so. The two windows are not bridged on purpose: an unprivileged program could otherwise make the elevated ForZip read protected files.

### Changed

- **ForZip opens maximized.** When a context-menu action brings back a minimized ForZip, it returns to the state it had (maximized, unless the operator resized it) instead of the normal size.
- **Extracting again goes to a new subfolder.** *Extract to subfolder*, *Extract…* and the destination suggested in Extract use `case (2)\` when `case\` already has something in it, instead of saving every repeated file as `name~2` mixed with the previous extraction. Two archives with the same name selected together get different folders. *Extract here* is unchanged: only clashing files are renamed, and nothing is overwritten.
- **Extraction errors are shown in red**, a wrong password among them.
- **Signature library updated for two security advisories.** `System.Security.Cryptography.Pkcs`, which signs and checks the manifest signature (CMS `.p7s`), went from 10.0.0 to 10.0.13: 10.0.0 is affected by [GHSA-846f-f764-76mx](https://github.com/advisories/GHSA-846f-f764-76mx) (high) and [GHSA-2fmv-rv2c-59x7](https://github.com/advisories/GHSA-2fmv-rv2c-59x7) (moderate). Signatures made before still verify the same; no project in the solution has a known vulnerable package left.
- **A folder Windows will not let ForZip read no longer stops the whole job.** Packaging the root of a drive failed with "Access to the path 'D:\System Volume Information' is denied", which even an administrator gets. Such a folder is now recorded among what was not included (reason `folder_unreadable`, with the Windows code and message, in the report and the manifest; the package is marked incomplete, CLI exit code 3) and the rest is packaged. The same applies to Hash Batch, the quick hash and `forzip hash`.
- The context menu and Settings say **context menu** instead of "right-click menu".
- **The delivery record shows the password twice**: first exactly as it is, for copying, and below it in groups of 4 for dictating or copying by hand, labelled as such. With only the grouped form it was unclear whether the spaces belonged to the password.
- **Hash Batch shows a grid**: column headers, the file name on the first line and its relative folder below, the size in KB/MB, and "could not be read" in red. The relative path alone in a narrow column made every row start the same way and cut off the name.
- **Choosing a large folder no longer freezes the window.** Folders are read in the background in Compress and Hash Batch (the root of a drive took several seconds with the window "Not responding"); a message says it is reading, and Compress or Calculate are enabled when it finishes. The root of a drive is listed as `D:\` rather than a bare `\`.

- **The extraction password no longer lingers.** It is cleared when another archive is loaded and after each run. A password left from a previous archive made the log record a `.tar.gz` and an ISO as "Encryption: Yes"; the log line now says whether a password was given, which is all ForZip knows at that point.
- **The redacted log says what it left out.** With the Reserved profile, lines whose subject is a name or a path read "… [omitted: Reserved profile]" instead of ending in an empty "finished successfully at:", which looked like a fault.
- The profile options read **Standard (.zip / .7z)** and **Reserved (.fzs)**, and the format control explains why it is locked to ZIP in the Reserved profile; the simple-mode hint says it packages as ZIP.
- **The ES | EN button saves the language**, as Settings does. It used to last only until ForZip was closed, so after reopening, reports came out in the previous language.
- **.NET 10.** ForZip moves from .NET 8, whose support ends on 10 November 2026, to .NET 10 (LTS). Certificate loading uses `X509CertificateLoader`; caller cancellation of the update check is now explicit; the transitive `Tmds.DBus.Protocol` (Linux-only, pulled in by Avalonia) is pinned to the fixed 0.21.3.
- The **Reserved profile always packages as ZIP**: the `.fzs` envelope carries a ZIP, which is what `fzs_extract.py` and `Open_FZS.html` read. The CLI rejects `--profile reserved` with 7z before writing anything, and the GUI locks the format control like the rest of what the profile governs. Simple mode also packages as ZIP (recommended defaults).
- **Links inside a selected folder are not followed.** Symbolic links and junctions are recorded among the files not included (reason `link_not_followed`, with their target, in the report and the manifest) instead of being walked into: a junction used to pull files from anywhere else on the disk into the package as if they were evidence, and one pointing back up the tree ended in a "path too long" error. Cloud placeholders (OneDrive) are not links and are read as before.
- **A package is never written over another one, nor inside what is being packaged.** If the output, any of its volumes, its manifest or its report already exists, the GUI suggests a free name (`case (2).zip`) and the CLI stops with the list of what is there. The default output no longer lands inside the evidence folder when the source is given with a trailing separator (`-i C:\case\`), and the folder chosen in Settings as default output is now used as such.
- **The `.fzs` format rejects a header declaring more than 10,000,000 KDF iterations** (spec §3, in ForZip, `fzs_extract.py` and `Open_FZS.html`): the header is only authenticated once the key is derived, and an altered value could keep a reader deriving for hours before the tampering showed.

### Fixed

- **A failed or cancelled extraction no longer leaves empty folders behind.** The files it had written were already removed, but the folders it had created stayed, starting with the destination: an empty `case (3)` that looked like a result. Now those go too — only the ones that extraction created, and only if empty; a destination that already existed is left as it was.
- **Hash Batch could save its report inside the folder it had hashed**, mixing the report and its `.sha256` with the evidence (and into the next calculation of that folder): the save dialog opened in the last folder used, usually the one just added. It now opens next to what was hashed, and a path inside a hashed folder is refused with a message before the operator dialog. The same check now recognises the root of a drive as containing everything on it, which also applies to packaging. `forzip hash -r` refuses a report path inside the hashed folder as well.
- **The report name kept a "(2)" it did not need when switching to text.** The free name was worked out for `.html`; changing the type in the save dialog kept it and only swapped the extension. If the operator did not touch the name, it is now recalculated for the chosen type (and folder); a typed name is kept as is.
- **The *Details* header of the context-menu Verify window** was highlighted only behind the word, not across the row.
- **Reserved profile: the password on screen changed after a cancelled run.** Cancelling the operator dialog marked the generated password as used, so the next run silently generated another one; a password copied from the screen in between did not open the envelope (the delivery record was right). The password now counts as used only once something encrypted with it stays on disk: an envelope, or leftovers that could not be deleted. The log no longer says "package created successfully" right before discarding it.
- **Verify kept the previous package's password** when another file was loaded, and a path that does not exist was reported as "invalid format"; it now says the file was not found.
- **An `.exe` that is not a self-extracting RAR** chosen in Extract gave "Cannot find central directory"; it is now refused, when loaded and when extracting, with a message saying so. It is never run.
- **A crafted encrypted 7z could hang ForZip forever.** The number of key-derivation rounds comes from the archive and had no limit: 2^62 rounds kept ForZip computing (for thousands of years) as soon as a password was given, and cancelling did not stop it. The engine now refuses more than 2^24 rounds, the same limit as 7-Zip.
- **Extraction stops before filling the disk.** A small archive built to expand enormously (a "decompression bomb") filled the destination disk until Windows failed; with the destination on C: the system was left without space for a while. ForZip now checks the free space as it writes and stops, discarding what it extracted, when less than 1 GB would be left. ISO images whose entries all point to the same data, so that a small image "contains" far more than its size, are refused when opened.
- **A small RAR can no longer make ForZip reserve 1 GB of memory per file** by declaring a huge dictionary: outside solid archives the window is sized to the file.
- **A file name longer than Windows allows no longer stops the whole extraction.** A name over 255 characters (an Autopsy report with long tags, for instance) cannot be created on NTFS: extraction stopped there and discarded everything already extracted, in ZIP, 7z, TAR and the other formats. Now that name is shortened, keeping its extension and adding a short fingerprint of the original (`~` and 8 hex digits) so that two long names that start alike do not collide; everything is extracted and the entry is listed among the renamed ones with its full original name.
- **Extract warns about paths Windows Explorer cannot open.** Files whose full path ends up longer than 259 characters are extracted correctly, but Explorer and many programs cannot open them; they are now listed at the end of the extraction (console and activity log), with the advice to extract again into a short-named folder near the root of the drive. It is a warning: the extraction is still complete.
- **Two selected folders with the same name and the same empty subfolder** (for example `A\docs\sub` and `B\docs\sub`) put that empty folder twice in the package, under the same name. It now goes once, in ZIP and in 7z.
- **Long file names no longer break the report's tables.** A name longer than the file column pushed the size and the hash of its row out of line; it now goes whole on its own line (a forensic report never shortens a name) and the size and hash follow below, in their columns.
- **`forzip zip --split` without a size was silently ignored** and the package came out in one piece. Any option that needs a value and arrives without one now stops the command with a clear message, like an unknown option does.
- **Generating a report in another language no longer switches the application's language back and forth.** The report takes its texts in its own language directly; before, the global language was changed and restored, which notified every screen twice and, in Compress, did so from a background thread.
- **Windows Alt codes typed other characters** in every ForZip text field: Alt+92 gave `┬` instead of `\` and Alt+64 gave `¶` instead of `@`, because the code Windows composed did not reach the UI framework intact. ForZip now composes it itself, with the same rule as Windows (no leading zero: OEM code page; leading zero, as in Alt+0169: ANSI code page). A backslash in a path or a symbol in a password typed this way could otherwise be wrong without anyone noticing.
- **Hash Batch logged "finished successfully"** when some files could not be read; the line is now a warning with how many were computed and how many were not.
- In the Reserved profile, log lines whose subject goes after the text ("Incomplete extraction at:") ended in the air; they now end with the omission marker.
- The About screen shows the official logo instead of two emoji; the remove button of the trusted signers list and the browse button in Verify are aligned.

- **Verifying a split package with its first volume missing said only "ZIP file not found".** The volumes listed in the manifest are now checked before the set is assembled: the missing ones are named, the ones present are each checked against their hash, and the verdict no longer suggests a missing password.
- **The Verify section stayed in the language it was first opened in**; it now follows the ES | EN switch like the rest.
- **A damaged or altered package was reported as "no alteration detected".** When the package could not be opened at all — a truncated ZIP, the first file of an AES-encrypted ZIP altered, an encrypted 7z altered — Verify gave the amber "incomplete verification" instead of "evidence compromised", because the package's global hash was compared inside the same step that reads the content and was skipped when that step failed. The global hash is now always compared on its own: if it does not match, the verdict is compromised; if it matches and the content cannot be read, the package is intact and the message says the password is missing or wrong. This also applies to the verification done when an envelope is opened.
- **An invalid signature no longer shows "trusted signer"** next to it (CLI and GUI): the certificate did not sign that file, so whether it is on the list means nothing.
- **Verifying an envelope whose package has its own password**: `forzip verify -i … --package-password` gives the package's password when it differs from the envelope's (a package sealed by hand), and the reason the content could not be verified is now printed, in the CLI and the GUI, instead of just "could not be verified".
- **An empty envelope is rejected** before asking anything: with no blocks there is nothing to authenticate the password, so it "opened" with any password. ForZip never seals an empty envelope.
- **The inner container of an envelope only accepts plain file names**: a `:` (a hidden NTFS stream), a reserved name, a trailing dot or two entries with the same name now reject the envelope instead of writing a hidden stream or overwriting the first file. Only a hand-made envelope can carry them.
- **Extracting an archive that has a file and a folder with the same name** (`k` and `k/`) no longer aborts: the folder is saved as `k~2` with everything inside it, and documented as renamed.
- **`forzip zip`** creates the output folder if it does not exist (as `unzip` already did, never inside the evidence), warns when `--operator`, `--case`, `--court`, `--hash`, `--sign-cert` or `--timestamp-url` are given without `--report` (nothing records them), and the report records the package's full path instead of the path as typed. The help for `unzip` lists RAR.

- **Extracting a ZIP did not check the CRC32.** A stored file with one byte changed was extracted with "completed successfully"; now the size and CRC32 of every entry are checked, and an entry that fails is set aside (see below). ZIP entry names follow the same rules as TAR, RAR and 7z: a `:` no longer writes a hidden NTFS stream into another extracted file, reserved names are renamed, and two entries with the same name are both kept and documented.
- **Extracting never overwrites a file that was already in the destination**: the extracted one is saved as `name~2` and documented. Before, it was overwritten, and if the extraction then failed the cleanup deleted it as if it were its own.
- **A stale package with the same name won over the new one.** After repackaging as volumes where a single `case.zip` already existed, verifying the new, correct package reported "evidence compromised" (it was checking the old file), and the Reserved profile would have sealed the old one. Fixed by never overwriting (above); a missing middle volume is now named instead of leading to a generic error.
- **7z packaging now fails, like ZIP, if a file changes size while being read**; the manifest used to declare the size seen when walking the source next to the hash of different content.
- **A sealed envelope is test-opened before it is handed over**, so a write failure can no longer leave an envelope nobody can open while the clear-text artifacts are deleted; the free-space check now accounts for the temporary container and the envelope living on the same disk.
- **The delivery record (`--acta`) is checked before sealing**: an existing record is never overwritten (it holds another envelope's password) and a missing folder is reported before any work, not after an envelope sealed with a generated password nobody would ever see.
- **Verification no longer overstates an envelope without its receipt**: without the receipt only the format is checked, so the CLI no longer prints "it is the same file that was sealed" in green and the GUI shows "incomplete verification" instead of "verified". An incomplete content verification is no longer labelled "invalid format". The verdict labels moved to the language files.
- **Reserved profile in the GUI: a fresh password for every package.** The password was only generated when switching into the profile. With Reserved as the saved profile, "New job" emptied the password and turned encryption off without anything restoring them, so the next package came out unencrypted, failed to seal and was left in clear text; without "New job", consecutive envelopes shared one password, so one delivery record opened the next envelope. Now each package gets its own.
- **Reserved profile: no envelope without the report and the manifest**, which are what the receipt stands for and what the content is checked against when the envelope is opened. If the operator dialog is cancelled the GUI no longer seals a bare ZIP: it discards the intermediate package and says why, as the CLI already required.
- **Reserved profile: a failed seal discards the intermediate package** (ZIP, report and manifest) in the CLI and the GUI. The generated password only reaches the delivery record, which is written once the envelope exists, so the encrypted ZIP could not be opened by anyone and the report and manifest were left in clear with the case data. The original evidence is not touched.
- **The signing certificate is checked before the long work**: `forzip zip` and `forzip seal`, the envelope builder and the GUI operator dialog reject a PFX that does not open (wrong password, damaged, no private key) before packaging or sealing. Before, a mistyped PFX password showed up when signing the receipt, after the whole envelope had been made, and left a receipt naming a deleted envelope; a receipt is no longer left behind when sealing fails after writing it.
- **The GUI showed a wrong envelope password as "NOT VERIFIED"**, the same as a tampered envelope. It is now "incomplete verification", as in the CLI; red is kept for what was found altered (envelope or receipt mismatch, a block that does not authenticate, content that does not match its manifest).
- **The CLI took a password starting with `-` as another option**: generated passwords include `-` among their symbols, so `forzip unseal -p` with the password from the delivery record failed for roughly one envelope in eighty. `-p`/`--password`, `--sign-cert-password` and `--cert-password` now always take the next argument.
- **`forzip seal` on a package made in the GUI left the report out**: the GUI names it `case.report.txt` (not `case.zip.report.txt`), so it stayed outside the envelope and, with `--delete-sources`, in clear text next to it. Both names are taken now. Sealing a folder no longer takes the envelope-opener page or temporary files left by an earlier sealing, and says which subfolders are not included instead of skipping them silently.
- **The redacted activity log of the Reserved profile no longer records paths**: Extract wrote the archive name and the destination folder in the message, and several errors carried file names in the exception text. Those parts now go as evidence detail, which redaction drops.
- **Verify in the GUI can check an encrypted ZIP or 7z package**: the password box, which only appeared for envelopes, also appears for a manifest. Before, an encrypted package always ended as "incomplete". The verdict label names what was verified (report, evidence, envelope) as the CLI does, and the Verify button is translated.
- **Files listed in the manifest without a hash are reported as "no hash"**, not as OK: only their presence was checked. A package with such files verifies as incomplete. Opening an envelope (CLI and GUI) no longer says "evidence altered" when nothing was found altered but not everything could be verified.
- **Verifying a ZIP no longer stops at the first damaged entry**: it is reported as altered and the rest is still checked, as with 7z. A wrong password is still reported as such.
- **Extracted files keep their modification time** when the archive states it unambiguously: 7z, RAR, TAR and the other third-party formats, and ZIP entries with an NTFS or Unix extended timestamp. A plain ZIP DOS time does not say its time zone (ForZip's ZIPs store UTC, Windows Explorer local time), so it is not applied rather than applied hours off.
- **A split disk image (`image.001`, `.002`… from dd) is no longer taken for a split ZIP**: Extract says it is not a package instead of a generic "invalid ZIP".
- **Opening an envelope that fails halfway leaves nothing in the destination** (full disk, cancellation): what was written is deleted, and the folder too if the opening created it.
- **After installing an update, ForZip comes back up**: the new version used to find the old window's single-instance lock still held, hand its (empty) arguments to the closing window and exit. The lock is released before relaunching. The help opens from a copy inside the executable, so after an update it is the new version's; the update notice says the command-line tool is updated separately.
- **The Reserved profile no longer overwrites the saved 7z preference** (also when used once from the context menu); leaving the profile brings the operator's choice back.
- **Sealing shows one progress run** for encrypting and test-opening, in the GUI (which showed none) and in the CLI (where the bar reached 100 % twice). The envelope is flushed to disk before the test opening.
- **A damaged file no longer costs the rest of the extraction.** When one file of a ZIP, 7z or RAR fails its check (CRC32, size, AES authentication, data that does not decompress), it is not left in the destination — neither under its name nor half-written — and is listed with its expected size and the reason; the other files are still extracted, each verified against its own check. The result is reported as an incomplete extraction (the CLI exits with code 3, like an incomplete package), never as a success. Before, the whole extraction was aborted and the good files deleted too. A wrong password (the first encrypted file failing), names escaping the destination and damage to the archive structure still abort everything, and so does any error in a compressed TAR or an ISO, whose files have no check of their own: there, what came before could not be vouched for. In a solid 7z or RAR the damage carries over to the files that follow in the same block, which are set aside as well.
- **A valid signature no longer passes for a known signer.** Verification showed only the certificate's name (`CN=…`), which whoever creates a certificate chooses: someone could alter the evidence, rebuild the manifest and sign it with a self-signed certificate bearing the same name, and the result looked the same. Verify (GUI and CLI) now shows the certificate's SHA-256 fingerprint and says whether it belongs to a **trusted signer** — a new Settings tab where fingerprints are registered by hand or read from a `.cer`/`.crt`/`.pem`/`.p7s`, and `--trusted-signer` in the CLI. Without a list, it says plainly that the signer's identity was not checked. Applies to manifest and receipt signatures; the TSA certificate's fingerprint is recorded too.
- **Verify no longer shows red when there is nothing to verify against**: a report without its `.sha256`, a ZIP without its manifest, or a RAR/TAR/ISO chosen with "Verify" ended as "NOT VERIFIED", like a tampered file. It is now "incomplete verification" with an explanation (CLI exit code 2); red is kept for an actual mismatch. The context menu no longer offers "Verify" on third-party formats, which never carry a manifest.
- **Hash Batch, quick hash and `forzip hash` work the same way.** A file that cannot be read (blocked by the antivirus, in use, deleted) no longer stops Hash Batch: it is marked and goes into the report as not read, with its Windows code (`forzip hash` exits with code 3). Folders can be added and are walked recursively without following links. Reports record each file's full path and modification time, use the algorithms the batch was computed with (not the ones ticked when exporting) and keep the case number, description and court entered in the operator dialog, which Hash Batch used to drop; that dialog no longer offers a signature Hash Batch would not make. The quick-hash report now lists unreadable files as such and is written with its `.sha256`.
- **The CLI rejects what it does not understand**: an unknown option (`zip -r`, where the option is `--report`) or algorithm (`-a sha3`) stops the command with the list of valid ones, instead of silently doing less than asked. Algorithms are accepted as `sha256`, `SHA-256` or `sha_256`.
- **ForZip starts from a read-only folder** (Program Files, a write-protected USB drive): configuration and activity log go to `%LOCALAPPDATA%\ForZip` when the executable's folder cannot be written; it stays portable otherwise. Before, the activity log folder could not be created and ForZip closed at startup. The configuration file, shared by the main window and the quick-hash window, is written atomically and retried when the other process is using it, instead of crashing; the activity log moves to the new day's file at midnight.
- **Selecting several archives and choosing Extract or Verify** loads the first one and lists the others in the activity log; before, each one replaced the previous and only the last one stayed, with no warning.
- The folder suggested for extracting `case.tar.gz` or `case.part1.rar` is `case`, not `case.tar` or `case.part1`.
- `-p` (and the other password options) no longer takes another ForZip option as the password: `-p --gen-password` is not a password.
- `forzip verify -i` accepts a manifest or a report, as the GUI does by extension; it used to treat anything given with `-i` as an envelope and answer "not a valid ForZip envelope".
- The folder-background context-menu entry works on a drive root: Explorer passes `"D:\"`, which the command line turned into `D:"`.
- `forzip seal` on a file only takes siblings that continue its name with a dot (sidecars and volumes); `case.zipold` used to go in, and `--delete-sources` deleted it.
- The GUI single-instance pipe only talks to the same user, so another account on the machine cannot receive the paths forwarded by a second instance.
- The update check's comment claimed the published SHA-256 protected against a compromised account; it only detects a corrupted download. Verifying the Authenticode signature is the real defence and depends on signing ForZip.

## [2.0.0] - first part, developed as 1.5.0 (2026-09-04, never published as such)

### Added

- **Sealed container `.fzs` — format core (no user interface yet).** Groundwork for the forthcoming Reserved confidentiality profile, whose purpose is that what leaves for third-party cloud storage is a single opaque file: no file names, no folder structure, no file count, no case data and no per-file hashes. A ZIP encrypts its contents but its central directory never is, and the report and manifest that must accompany a package travel in the clear — so the package as a whole is wrapped instead. The container is AES-256-GCM over 1 MiB chunks, with the key derived by PBKDF2-HMAC-SHA256 at 600,000 iterations (replacing, for this envelope, the PBKDF2-HMAC-SHA1 at 1,000 iterations that the WinZip AES scheme imposes inside the ZIP). Its plaintext header carries only what is cryptographically indispensable — a random package id, the sealing date, the KDF and cipher parameters and the payload size — and is authenticated as the AAD of every chunk, so altering the iteration count, the salt or the declared size breaks decryption at the first chunk. The chunk index goes into both the nonce and the AAD, which makes reordering detectable, and a final-chunk marker plus the authenticated chunk count make truncation detectable. Sealing and opening both stream, so a package of tens of gigabytes is neither loaded into memory nor duplicated on disk, and a failed or cancelled run never leaves a partial envelope on disk. Argon2id was deliberately not adopted: it would add an external dependency and widen the audit surface of a forensic tool.

- **Public receipt, two-level verification and key handover record (still no user interface).** The second half of the sealed-container groundwork, and the part that makes the envelope usable as evidence rather than merely opaque. Integrity and confidentiality are deliberately split into two artefacts: the envelope holds the content, and a separate `.receipt.json` proves the envelope is the one that was sealed and who sealed it — without naming a single file, path, case number, court, operator or per-file hash. Its content is closed by specification and a test fails if any field ever appears that is not on that list, because the next leak would arrive as a well-meaning extra field. It is signed with the existing CMS/PKCS#7 signing service, RFC 3161 timestamping included, reusing that code unchanged. Verification accordingly has two levels and resolves which one applies on its own, accepting either the `.fzs` or the receipt and finding its counterpart: the **public** level needs no password and answers the question that goes into the court file — the envelope is intact or it was altered, signed by whom and when; the **full** level takes the password, decrypts the envelope in a temporary folder that is removed even when the run throws or is cancelled, and produces the same per-file verdict against the internal manifest that ForZip has always produced. A missing or unreadable receipt degrades the public level rather than failing it, and says so: the format still checks out, the origin no longer does. Finally, sealing a package produces a printable key handover record — the package fingerprint, the password grouped in blocks of four so it can be transcribed by hand, the case data, blank fields for the recipient to sign, plain-language instructions for opening the envelope years from now, and a prominent warning not to open it inside a folder synced with Drive, OneDrive or Dropbox, where the contents would go up in the clear on their own. The record is never written to disk automatically.

- **The sealed container reaches the command line.** `zip --profile reserved` runs the whole Reserved flow in one command: it packages exactly as it always has, then seals the ZIP and every sidecar into the envelope, emits the receipt, writes the key handover record and deletes the intermediates, so what is left on disk is the envelope and its receipt and nothing in the clear. The profile governs what it must govern rather than leaving twelve checkboxes for the operator to get wrong: encryption on, a generated 32-character password, manifest, report and `.sha256` all produced. It insists on `--acta <path>` precisely because the generated password is written there and nowhere else — not to the console, not to a log, not to `config.json` — and a package whose password was never recorded is a package nobody can open. `seal` does the same for a package that already exists, taking a folder or a file (whose split volumes and sidecars it picks up on its own), and `unseal` opens an envelope back into its parts. `verify` now also accepts `-i` with either the `.fzs` or its receipt, finds the counterpart itself, and picks the level from whether a password was given; its exit codes distinguish an intact envelope (0) from one that could not be fully checked (2) and one that was altered (3), which is what a script in a lab pipeline needs to branch on. Passwords are read from the console with the echo off whenever the option is omitted, and the help says why that is the better habit: a password on the command line stays in the shell history and in the process list, which for a key handed over in person under signature defeats the entire procedure.

- **Reserved confidentiality profile, in the interface.** The Compress screen now opens with a single decision above everything else: Standard, which behaves exactly as ForZip always has, or Reserved, which seals the finished package into an opaque `.fzs` envelope and emits its public receipt. It is one decision rather than a grid of checkboxes, because on sensitive material twelve independent switches are a silent error waiting to happen — untick the wrong one and nothing tells you until the file is already uploaded. Choosing Reserved fixes encryption, a generated 32-character password, the manifest, the report and the sidecar; the controls it governs stay visible but disabled, with a tooltip, so it is clear what changed rather than mysteriously absent. The result screen is rebuilt around what the operator must do next: which file goes to the cloud (only the envelope), which goes into the case file (the receipt), and the key handover record, shown on screen with the password grouped for transcription and never written to disk unless a path is chosen by hand. Picking Standard raises a one-per-session notice that names and sidecars stay in the clear — shown once, because a warning that always appears stops being read.
- **Verification of sealed envelopes from the interface.** The Verify screen accepts a `.fzs` or its receipt, finds the counterpart itself, and offers a password field only when it applies: leave it empty for the public verdict that goes into the case file, fill it in for the file-by-file verdict as well.
- **Detection of cloud-synced folders.** The likeliest leak in this whole design is not cryptographic: it is someone extracting an envelope inside a folder synced with Drive, OneDrive or Dropbox, where the material uploads itself, in the clear, with no decision and no trace until it has happened. ForZip now looks for the markers those clients leave at the root of what they sync, walking up from the path so a destination three levels deep is still caught, and warns on the packaging destination. On the command line `unseal` refuses outright unless `--allow-cloud-folder` is passed — a script cannot answer a confirmation prompt, so aborting with a clear message beats hanging. The detection is heuristic and can be wrong in both directions; it errs toward warning, because a false positive costs a click and a false negative costs the evidence.
- **Redaction mode in the activity log.** Under the Reserved profile the log records the operation and the package identifier and nothing derived from the evidence: no file names, no source paths, no case data. It is a mode rather than a text filter applied after the fact — each entry separates its safe part from its sensitive one, and the sensitive part is dropped entirely rather than shortened, because a half-masked path still says which case is being worked on.
- **Context-menu entry for sealed envelopes.** `.fzs` files get *Verify envelope (ForZip)*, and only that: opening an envelope stays a deliberate act inside the application. The public receipt gets the same entry, filtered with `AppliesTo` so it shows on `*.receipt.json` and not on every JSON file: whoever holds the case file usually has the receipt, not the envelope, and ForZip finds the pair. Files, folders and folder backgrounds gain *Pack into a reserved envelope (ForZip)* next to the usual entry, which opens the Pack screen with the Reserved profile already chosen — aimed at the likeliest mistake, forgetting to switch profile before uploading something to the cloud.
- **The `.fzs` format is published, and there is a hundred-line extractor that does not need ForZip.** A format of one's own solves the problem of unwanted extraction — no third-party cloud app knows what to do with a `.fzs` — but it introduces a worse one: that in ten years the evidence is unreachable because the tool no longer exists or no longer runs. In court that is the argument the defence will make, so three cheap measures close it. `Documentation/Formato_FZS_v1.md` specifies the container in public: binary layout, KDF parameters, nonce and AAD construction, the verification algorithm and the security limits, at the level of detail needed for a third party to write their own extractor without reading a line of C#. `Tools/fzs_extract.py` is that extractor, in about a hundred lines of Python 3 needing only the standard library plus `cryptography`; it asks for the password, decrypts the envelope and writes the internal container to disk, and nothing else — no interface, no forensic logic, no manifest checking. It was written **from the specification and not from the code**, which is the whole point: a new integration test seals a package with ForZip, opens it with the script and compares byte for byte, so if the two ever diverge one of them is wrong and it has to be found out which. A copy of the script now travels inside the internal container of every envelope as well. None of this weakens anything — the security of an envelope rests on its password, never on the secrecy of its format, and a cryptographic format whose protection depends on nobody knowing how it works is not a secure format. The README carries the third measure, which is procedure rather than code: the organization must archive the exact executable of every version used in production, with its SHA-256, in its own internal registry, because reproducing a verification years later means running the same tool that produced it.
- **The interface can open an envelope, not just verify it.** Until now the GUI only verified a `.fzs` — decrypting to a temporary folder and deleting it — so a recipient with ForZip installed had no way to get the content short of the command line, while the handover record told them to choose *Verify*. The Extract screen now accepts a `.fzs`: it shows the identifier and sealing date from the clear header, asks for the password and a destination folder — deliberately with no default, since an envelope downloaded from the cloud usually sits in a synced folder — stops with a confirmation whose default is *Choose another folder* if the destination is synced with Drive, OneDrive or Dropbox, opens into an `FZS-…` subfolder of its own (opening never overwrites anything), and then verifies the content against the manifest inside and shows the verdict. The logic lives in a shared `SealedPackageOpener`, which `forzip unseal` now uses too: the CLI gains the same verification (exit code 3 if the content does not match) and refuses a non-empty destination. `.fzs` files get their own file type when shell integration is on — the ForZip icon and a double-click that loads the envelope into the Extract screen without decrypting anything — added without taking over the extension if another program already claimed it, and removed without touching anything that is not ForZip's. The context menu gains *Open envelope…*, which does the same. The handover record now says *Extract*.
- **An opener for whoever receives an envelope, in a single HTML page.** The Reserved profile had a delivery problem: the recipient got a format of its own and needed ForZip — or Python plus `cryptography` and a console — to open it. `Tools/Open_FZS.html` is one self-contained file that runs offline in Edge or Chrome: choose the `.fzs`, check the password (only the first block is decrypted, so a wrong password never gets as far as asking where to save), choose a destination, and the inner ZIP comes out. Nothing to install, no administrator rights, no script host, and no unsigned executable for SmartScreen to distrust. ForZip leaves a copy next to every `.fzs` and its receipt (it is the same page for every envelope and holds nothing of the package), and the key handover record now explains opening with it first and states its SHA-256, with the `certutil` command to check it. A Content-Security-Policy in the page forbids every connection; the code is unminified. It decrypts block by block and writes through the browser's transactional writer, committed only after the last tag validates: a 2 GB envelope opened in 8 seconds with a 121 MB memory peak, and an altered block or a cancellation leaves zero bytes behind. Wrong password, truncation, extra data, altered block (named by index), foreign file and future format version each get their own message, in Spanish or English. Its decryption core lives in a separate `<script id="fzs-nucleo">` block; the tests run that exact block in Node — same Web Crypto as the browser — and require output identical byte for byte to ForZip's, plus static checks that the page loads nothing external and never touches storage or the console.

### Changed

- **The packaging screen is two columns, and the destination no longer hides behind the log.** With the activity log open the usable area is 848 × 448 px, and the form in a single column asked for about 620 px of height — so the output path, the progress bar and the buttons scrolled away underneath the log exactly when there was something to watch. Width was the only thing to spare: the evidence now sits on the left (drop zone, file count, and a file list that takes whatever height is left and is the only thing on the screen that scrolls), everything that gets decided sits on the right, and the destination with its button is pinned to the bottom where it cannot leave the view. The confidentiality profile was not shrunk to make room — it keeps its border, its heading and its full explanation; what changed is that it stopped standing in the vertical path of everything else. In the narrower right-hand column the password field and its three buttons share the width through a grid instead of fixed sizes, and the advanced options put their labels above their controls rather than beside them, so nothing is cut off at the minimum window width.
- **The interface stopped speaking in voseo, and "Comprimir" became "Empaquetar".** Fifteen strings carried Argentine second-person forms — *Arrastrá*, *hacé*, *Verificá*, *Elegí*, *Guardá*, *podés* — that read as chatty in a tool whose output is filed in court; they are now impersonal infinitives. Two drop-zone captions in the Extract and Verify screens turned out to be hardcoded in the views, bypassing the string files entirely (one of them printing a duplicate line); both moved to the localized strings. And the action is called packaging throughout — the screen title, the sidebar, the Explorer context menu, the file pickers and the bundled help — because that is what it is: the compression level is one setting inside it. The forensic report's own wording is untouched, so packages still compare byte-for-byte against the 1.4.0 reference.
- **The sidebar has real icons instead of emoji.** Seven glyphs of its own — package, extract, hash, verify, key, settings, about — replacing the four colour emoji, two text glyphs and a bare `#` that shared no stroke, no weight and no optical size, and whose colour came from the system font rather than from ForZip. They are monoline: one geometry per icon, painted with whichever brush the state calls for, which is what lets the same file serve the dark and the light theme; a two-tone fill would need two brushes per icon and one set per theme. Drawn in a 24×24 space and shown through a `Viewbox`, with an explicit box and `Stretch="None"` so every icon keeps the same optical size — without that each one scales to its own bounds and the glyph that fills less of its box looks bigger. Three of them were redrawn after being seen at their real size rather than at sketch scale: the fingerprint inside the package box collapsed into a blob when two concentric arcs landed 2 px apart, and a document plus a legible `#` simply do not both fit in fifteen pixels, so Hash Batch keeps the numeral — the thing that names the section — framed in a tile.

- **Buttons have a little relief.** A short shadow below plus a one-pixel highlight along the top edge; the piece lifts on hover, and pressing inverts the shadow inward rather than enlarging it. On a dark background a black shadow alone is very nearly invisible — it has almost nothing to cast against — so the highlight does most of the work. Buttons with no fill, in the sidebar and the link-styled ones, are deliberately left flat: a shadow under a transparent control reads as a rectangle floating on its own. This needed `ClipToBounds="False"`, since a button clips its template to its own bounds and the shadow, drawn outside them, was reduced to a one-pixel sliver.
- **Closing asks first.** Closing the window by accident used to end the session outright. Now ForZip asks — and if an operation is running it says so plainly, because closing there leaves the package half written and useless as evidentiary material. In both cases the accented, focused button is the one that keeps the work: a reflexive Enter closes nothing.

- **The quick hash window no longer starts computing on its own.** Opening *Calculate hash (ForZip)* from the context menu now lists the selected files as *Pending* and waits: the operator ticks the algorithms and presses *Compute*, 7-Zip style. Reading a multi-gigabyte file is a decision, not a side effect of opening a menu. Algorithm checkboxes are disabled while a batch runs, a *Cancel* button replaces *Compute* for the duration, and cancelling keeps whatever was already computed. *Copy* and *Export* stay disabled until there is at least one hash to copy.

- Version raised to 1.5.0; the bundled help documents the Reserved profile, the two verification levels and, explicitly, what this version does not solve — the envelope's size still reveals the order of magnitude of its contents, and a copy of the evidence still lives on a third party's infrastructure.

### Fixed

- **A file that the antivirus or EDR will not let anyone read no longer stops the whole package.** Seen in production on Autopsy reports with e-mail attachments: one flagged attachment made ForZip abort, and operators went back to 7-Zip. Testing against a live Windows Defender showed why 7-Zip "worked": the identical `7z.exe`, copied under another name, is blocked exactly like ForZip — the workstation had a Defender exclusion for 7-Zip, and no way of opening a file avoids the block. ForZip has no malware scanner and cannot read what the system denies (`ERROR_VIRUS_INFECTED`/`ERROR_VIRUS_DELETED`). It now opens each evidence file before creating its ZIP entry; when the security software denies the read, the file is left out and the packaging continues. The omission is never silent: the report states *INCOMPLETE* in its parameters and gains a *Files not included* section with source path, size, timestamps, the Windows code and message, and the grounds for the omission (ACPO principle 3, ISO/IEC 27037:2012, NIST SP 800-86, RFC 3227) — stating explicitly that this does not certify the rest of the package as malware-free. The manifest lists them under `OmittedFiles` (schema 1.2, used only when there are omissions; a complete package still writes 1.1 and is byte-for-byte what 1.4.0 produced), verification does not report them as missing, the result screen shows an incomplete-package warning that other notes cannot overwrite, and the CLI lists them and exits with code 3. A block in the middle of reading a file still aborts, because the ZIP entry is already open and cannot be withdrawn. Testing the interface turned up a second route to the same silent omission: browsing to the folder in the Windows selection dialog, which runs inside ForZip's process, made Defender detect the attachment and quarantine it before packaging began, so the package came out "complete" with 50 of the 51 files selected. The interface now keeps a snapshot of what the operator saw when adding each source, and anything missing at packaging time is recorded as *present when selected, absent when packaging*, with the time it was seen; a file that vanishes between being listed and being opened is recorded instead of aborting the job. The report states the facts and names quarantine only as a possible cause, and the manifest gives each omission its reason (`security_software_blocked`, `missing_at_packaging`, `vanished_during_packaging`). Any security block that does abort now names its stage (reading evidence, writing, re-reading, sealing), the file and the Windows code, both on screen and in the log.

- **The quick hash window came up blank and showed no progress.** `HashService` awaited its reads without `ConfigureAwait(false)`, so every 64 KB block returned to the caller's synchronization context and ran `TransformBlock` on the UI thread — which was therefore hashing instead of painting, leaving an unrendered window until the file was done. The hash now stays off the UI thread entirely, and a regression test fails if the caller's context is ever used again.
- **The report stage looked like a hang.** Once packaging finished, generating the forensic report reported nothing at all — and its expensive step re-reads the whole package to compute the archive's global SHA-256, which on multi-gigabyte evidence is minutes of a frozen-looking window. Worse, the report text and the manifest were being built on the UI thread, so on packages with thousands of files the window stopped repainting entirely: the same defect already fixed in the quick hash window, in a second place. The stage now names what it is doing — global hash, report, manifest, signature, sidecar — with a real by-bytes bar on the hashing step, the elapsed clock keeps running, and the estimate resets to `--:--:--` rather than carrying over a figure from the previous stage that no longer means anything. Building the report text moved off the UI thread, and `HashService` gained an overload that takes a stream's known total size so the split-archive case (where the logical file does not exist on disk) reports progress too.
- **The Reserved profile's password shrank when regenerated.** The key button called the generator with a fixed length of 16 regardless of profile, so a package sealed under the Reserved profile — whose specification fixes 32 characters with a floor of 24 — silently dropped below its own declared minimum the moment the operator asked for a new password. The button now follows the profile.
- **The scrollbar sat on top of the controls.** In the packaging, extraction, verification and settings screens the vertical scrollbar was drawn over the content flush against the right edge, cutting through the *Advanced mode* switch and the *Clear all* button. The scrolled content now leaves it room.

- **The progress bar only moved between files.** The quick hash window passed `null` for the `IProgress<double>` that `HashService` already exposed, so a single-file selection — the normal context-menu case — jumped straight from 0 to 100 with nothing in between. Progress is now reported by bytes read, both as an overall bar for the batch (with the current file's name and its position in it) and as a per-file bar with a percentage. Reports are throttled to one per thousandth of the file so large files do not flood the dispatcher, and always close at 100 %.

- Nothing in the Standard profile changed, and a regression test now proves it against a package built by an actual 1.4.0 binary compiled from its tag: with source timestamps restored, the ZIP that 1.5.0 produces is byte-for-byte identical, and a package made by 1.4.0 still verifies here.

## [1.4.0] - 2026-07-28

### Added
- **In-app update installation, user-initiated and checksum-verified.** The *Check for updates* flow shipped in 1.3.0 could only point at the release page; it can now perform the update. Pressing *Update now* asks for confirmation (stating that ForZip will close and reopen), downloads the release binary matching the running executable's own file name, and **verifies its SHA-256 against the `.sha256` published alongside it**. Only on a match is anything touched — a mismatch or a missing checksum discards the download and installs nothing, because replacing a forensic tool's binary with something unverifiable would be blind remote code execution. The running executable is renamed to `<name>.old` (Windows permits renaming a running image), the new one takes its place, and ForZip relaunches itself; no helper process or batch script is involved, which also avoids the antivirus heuristics that pattern triggers. The `.old` copy survives until the next startup as a rollback, and is deleted then. After relaunch, ForZip opens About with a summary of which version it came from and the release notes, cached in `config.json` before restarting so they display even without a connection. Updating stays unavailable — with an explanatory message rather than a failure — when the release has no asset matching this executable or when its folder is not writable (read-only media, missing permissions), both normal situations for a portable forensic tool.

### Changed
- Sidecar `.sha256` parsing moved to a shared `Sha256Sidecar` helper in Core, used both by report verification and by the updater; `ReportService` now delegates to it.

## [1.3.0] - 2026-07-28

### Added
- **Quick hash window from the context menu**: *Calculate hash (ForZip)* no longer opens the full application. It launches a single self-contained window (7-Zip style) listing, per file, the name, full path, size, UTC modification timestamp and the selected hashes. Algorithms can be toggled in place (already-computed hashes are reused, only what is missing is read from disk again). The result can be copied to the clipboard as plain text or exported as a `.txt` forensic report in the standard ForZip format (UTF-8 with BOM), taking the operator data from the saved configuration without an extra dialog. A multi-file Explorer selection — which Windows launches as one process per file — is coalesced into a single window through a dedicated single-instance channel (`ForZip.QuickHash`), kept separate from the main application's channel so a quick hash never lands inside an open ForZip window.

- **Update check (manual, no self-update)**: a *Check for updates* button in About queries the project's latest published release and reports whether a newer version exists, showing its release notes inline and offering to open the release page in the browser. Optionally the check also runs at startup — **off by default** (`CheckForUpdatesOnStartup`), since it is the only network connection ForZip initiates on its own; when it finds something, the About entry in the sidebar gets a discreet dot rather than a dialog. ForZip deliberately **does not download or replace its own binary**: the report declares which version produced each piece of evidence, and many labs run validated, frozen tool versions, so changing version must stay an explicit operator decision. Failure to reach the network is reported inline and never interrupts work.

### Changed
- **The password generator no longer emits ambiguous characters**. Exclusion of `0 O o I l 1 |` used to be an opt-in checkbox (off by default); it is now unconditional and the option is gone. Rationale: a forensic password is transcribed and dictated by hand, so a character that cannot be read unambiguously is a transcription error waiting to happen. The effective pool is 87 characters with all classes enabled (24 uppercase + 24 lowercase + 8 digits + 31 symbols); entropy reporting already accounts for the reduced pool. CLI `genpass` drops `-a|--avoid-ambiguous` and documents its options in `--help`.
- **Password length is now typed as well as dragged**: the generator has a numeric field next to the slider, both bounded to 8–128 and clamped in the ViewModel so out-of-range typing is corrected instead of raising. The 8-character minimum was already enforced by `PasswordService`; the bounds now live in `PasswordOptions` (`MinLength`/`MaxLength`/`DefaultLength`/`AmbiguousChars`) as a single source of truth shared by Core, CLI, GUI and tests.
- Algorithm display names and their canonical order moved to `HashAlgorithmNames` (Core.Models); `ReportService` now delegates to it instead of keeping a private copy.

### Fixed
- **The bundled help page (`Help_ForZip.html`, opened from About) was stuck at "v0.9.0 Beta"** and documented only the 1.0-era feature set. It now declares the current version and covers everything shipped since: split archives, evidence verification and manifest signing with RFC 3161 timestamping, the Explorer context menu and its quick hash window, the password generator, simple/advanced compress modes and the CLI. A test (`HelpPageTests`) now fails the build if the version stated in the page ever drifts from `AppInfo.Version` again.
- **Saving from the Settings view silently reset settings owned by other views.** `Save()` built a brand-new `AppConfig` from the fields on screen, so `SimpleMode` (written by the Compress view) and `TimestampServerUrl` went back to their defaults every time the user pressed Save in Settings. It now loads the stored configuration and overwrites only the fields that screen actually edits.
- **The help page no longer pulls a font from Google Fonts.** A portable forensic tool that advertises "no telemetry" should not make a network request when its own documentation is opened — and on an offline or air-gapped workstation the request just failed and the typography silently degraded. The page now uses a local system font stack and is fully self-contained.

## [1.2.0] - 2026-07-03

### Added
- **Simple mode (guided) in the Compress view**: a toggle switches between *Simple* (drop the evidence, review, one big "Package evidence" button — ForZip enforces the recommended forensic defaults: SHA-256 per file, report, manifest and sidecar; technical options hidden) and *Advanced* (the full previous screen). The chosen mode persists in `config.json` (`SimpleMode`). AES-256 password protection remains available in both modes.
- **Result screen after packaging**: on success the Compress view shows a plain-language summary of every generated artifact (`.zip`/volumes, `.report.txt`, `.manifest.json`, `.sha256`, `.p7s`) explaining what each file is and why it must stay with the package, plus the global SHA-256 fingerprint with *Copy fingerprint*, *Open folder* (Explorer with the file selected) and *New package* actions. If the operator dialog is cancelled, the screen warns that the evidence won't be verifiable later.
- **RFC 3161 trusted timestamping** of the manifest signature: `SignatureService` can request a timestamp token from a TSA (e.g. DigiCert) and embed it in the CMS signature as the standard `id-aa-timeStampToken` unsigned attribute, making the signing date verifiable by third parties (unlike `signingTime`, which is signer-declared). Verification validates the token against the signature (`Rfc3161TimestampToken.VerifySignatureForSignerInfo`) and reports timestamp, validity and TSA identity in CLI `verify`/`sign` and in the GUI Verify view; an invalid token marks the evidence as compromised. If the TSA is unreachable the signature is still written and a specific warning (`TimestampUnavailableException`) is surfaced. CLI: `--timestamp-url` on `zip`, `-t|--timestamp-url` on `sign`. GUI: timestamp checkbox (default on) + TSA URL in the operator dialog; default TSA configurable (`TimestampServerUrl` in `config.json`). Verified end-to-end against `http://timestamp.digicert.com`.
- **Case data in the GUI operator dialog**: case number, description and court (previously CLI-only via `--case`/`--court`) now flow into the report and manifest.
- **Context-menu self-repair on startup**: if the integration is registered but points to an executable that no longer exists (moved folder, USB drive letter change), ForZip silently re-registers with its current path when the window opens. It never overwrites a registration whose executable still exists (another live copy).
- **First-run integration offer**: on a PC where ForZip was never integrated, a one-time dialog (per machine/user, tracked in `HKCU`) offers to add the context menu — one click instead of discovering Settings → Integration.
- **Verify on `.p7s` files**: right-clicking a detached signature now offers *Verify with ForZip*; the GUI resolves `x.manifest.json.p7s` to its manifest (also when dropped onto the Verify view).

### Changed
- **Version centralized in `AppInfo` (Core)**: GUI (window title, sidebar, About), CLI `--version`, the forensic report and the manifest all read the same constant; assembly `<Version>` set in the three projects. Fixes the stale `v1.0.0` shown in the sidebar.
- The Compress view is fully localized (browse buttons, encryption label, tooltips, progress labels and file-picker titles were hardcoded in Spanish).

### Fixed
- **Context-menu language now follows the app language**: the Explorer menu labels are stored in the registry at registration time and were never refreshed. Now they are rewritten when the app language changes, refreshed (idempotently) on startup, and headless `--register-shell` uses the language saved in `config.json` instead of the OS auto-detected one. Only applies when the registration belongs to the current executable.
- **"Juzgado" renamed to "Dependencia judicial"** in the case form (requests may come from a prosecutor's office, not only a court): full label + example watermark in the operator dialog, short label ("Dependencia"/"Authority") in the report to preserve column alignment, and updated CLI help for `--court`.
- **Activity log now follows the UI language**: every log entry emitted by the GUI (packaging, extraction, hashing, signing, navigation, shell integration) plus the log console title/tooltips and the Verify details pane were hardcoded in Spanish and now come from the es/en string resources.
- **Windows context-menu integration (portable)**: optional right-click menu in Explorer, 7-Zip/WinRAR style, registered under `HKCU` — no installer, no admin, fully reversible. Context-sensitive cascading "ForZip" submenu: *Compress / Hash* on files & folders, *Extract here / Extract to subfolder / Extract… / Verify / Hash* on `.zip` and `.001` volumes, *Compress* on folder background. Toggled from **Settings → Integration**; also scriptable headless via `--register-shell` / `--unregister-shell` / `--shell-status`. The GUI now accepts a verb + path on launch (`compress|extract|extract-here|extract-to|hash|verify`) and opens the matching view with the file(s) loaded. Pure layout/parsing logic lives in `ForZip.Core.Shell` (tested); registry I/O is Windows-guarded in the GUI. *(The GUI project now targets `net8.0-windows` to use the built-in registry APIs.)* A fail-safe **single-instance** coordinator (mutex + named pipe) forwards a multi-file selection to the running window so they accumulate in one place instead of opening several windows.
- **GUI verification parity for split archives**: the Verify view now lists the per-volume verdict and surfaces `ContentVerificationError`, distinguishing "compromised" (tamper detected) from "verification incomplete" (e.g. content couldn't be decrypted) — matching the CLI.
- **Split archives (multi-volume)**: optionally divide the output into fixed-size volumes (`.001`, `.002`, …), 7-Zip style, via `ZipOptions.SplitSize`. Hashing and splitting happen in the same single pass: each volume's SHA-256 is computed on the fly (`SplittingWriteStream`). Extraction and verification auto-detect and reassemble the volumes transparently through a seekable concatenated stream (`ConcatenatedReadStream`); the logical archive is never materialised as a single file on disk.
- **Forensic manifest v1.1**: records `isSplit` and a per-volume list (`fileName`, `size`, `sha256`); the report `.txt` gained a volumes section. The global `zipSha256` remains the hash of the *logical* archive, so content verification is identical for single-file and split archives.
- **Per-volume verification**: `VerifyArchiveAsync` issues an independent verdict for each volume (OK / altered / missing). This runs before content verification and is preserved even if the payload cannot be decompressed/decrypted (`ArchiveVerificationResult.ContentVerificationError`), so a damaged or tampered volume is still pinpointed when the password is missing.
- **CLI `--split <size>`** with suffix parsing (`700M`, `4096MB`, `1.5G`, `100K`); `unzip`/`verify` accept the `.001` volume directly. **GUI**: a "split into volumes" toggle with preset/custom sizes in the compress view; the extract view accepts `.001` files.

## [1.1.0] - 2026-06-01
